================================================================================
ALPHA ENGINE ARCHITECTURE
================================================================================

Scope:
- C++23, single process
- Binance USD-M perpetuals: BTCUSDT, ETHUSDT, SOLUSDT
- Latency-sensitive hot path with isolated control paths

Purpose of this file:
- document data/control flow and thread responsibilities
- define failure behavior and recovery paths
- describe what is production-usable vs still evolving

Note:
- environment variable details are documented in `docs/ENVIRONMENT_VARIABLES.md`

--------------------------------------------------------------------------------
1) SYSTEM TOPOLOGY
--------------------------------------------------------------------------------

Hot path (decision critical):

  Binance WS -> Parser -> MdEvent SPSC -> Main loop -> L2Book -> Strategy
      -> OrderManager -> PreTradeRisk -> Gateway -> Exchange REST

High-level picture:

  [Binance WS: fstream or demo stream host]
           |
           v
  +------------------+
  | BinanceWsClient  |  (dedicated thread, pinned HFT_CORE_WS)
  +------------------+
           | combined JSON frames (bookTicker, depth@100ms, aggTrade)
           v
  +------------------+
  | BinanceParser    |  normalize -> MdEvent
  +------------------+
           | push (non-blocking)
           v
  +------------------+     +------------------------+
  | SPSC Ring        | --> | MAIN THREAD (hot loop) |
  | (MdEvent)        |     | HFT_CORE_MAIN          |
  +------------------+     +------------------------+
                                    |
                    +---------------+---------------+
                    |               |               |
                    v               v               v
              L2Book x3      StrategyEngine    OrderManager
              (per symbol)   (OrderIntent)     (OrderCommand)
                    |               |               |
                    |               +-------+-------+
                    |                       |
                    |                       v
                    |               PreTradeRisk (limits + kill switch)
                    |                       |
                    |                       v
                    |               BinanceGateway (signed REST)
                    |                       |
                    v                       v
         snapshot_req_queue       HTTPS demo-fapi or fapi
                    ^
                    |
  +---------------------------+
  | Snapshot thread           |  REST GET /fapi/v1/depth (same mode as gateway)
  | HFT_CORE_SNAPSHOT         |
  +---------------------------+
                    |
                    v
            snapshot_res_queue
                    |
                    +------------------------------> MAIN THREAD (seed/reseed books)

Control and observability paths:

  UserStream WS -> exec_report_queue (SPSC) -> Main loop -> OMS
  Main loop -> SnapshotReq SPSC -> Snapshot thread -> SnapshotRes SPSC -> Main
  Reconcile thread -> remote openOrders snapshot -> Main healing checks
  Main loop -> ExecAudit SPSC -> audit writer thread
  Main loop -> MdHealth SPSC -> health writer thread

This split keeps network/recovery/logging work away from the strategy decision loop.

--------------------------------------------------------------------------------
2) THREAD MODEL
--------------------------------------------------------------------------------

Thread roles:

- WebSocket thread (`HFT_CORE_WS`)
  - receives combined market-data stream
  - parses/normalizes into `MdEvent`
  - pushes to lock-free SPSC queue

- Main thread (`HFT_CORE_MAIN`)
  - consumes market data
  - updates per-symbol books
  - runs strategy trigger gating and intent generation
  - executes order management, risk checks, and gateway sends
  - consumes exec reports and applies OMS transitions

- Snapshot thread (`HFT_CORE_SNAPSHOT`)
  - handles depth snapshot reseed requests
  - returns snapshot results asynchronously

- User stream thread (typically same affinity class as control threads)
  - manages listenKey and order-trade update stream
  - emits normalized execution reports

- Reconcile thread (`HFT_CORE_RECONCILE`, optional)
  - periodically fetches signed `openOrders`
  - provides remote-state signal for mismatch/heal checks

- Writer threads
  - execution audit writer
  - market-data health writer

Scheduling notes:
- optional realtime mode (`SCHED_FIFO`) and `mlockall` are available
- hot and control threads should be pinned to separate cores
- all control-path loops are bounded to prevent tail-latency blowups

--------------------------------------------------------------------------------
3) MARKET DATA PIPELINE
--------------------------------------------------------------------------------

Inputs:
- combined websocket streams for `bookTicker`, `depth@100ms`, `aggTrade`

Processing:
1) websocket frame parse and normalize into `MdEvent`
2) non-blocking enqueue to SPSC ring
3) main loop consumes events and mutates per-symbol `L2Book`

Book integrity:
- depth sequencing uses Binance bridge constraints (`U/u/pu`)
- snapshot-seeded warmup establishes continuity
- if continuity is lost, symbol is gated and resnapshot requested

Liveness:
- main loop tracks websocket message age
- idle timeout triggers reconnect with cooldown
- reconnect events are emitted via MD health logger

--------------------------------------------------------------------------------
4) STRATEGY AND INTENT GENERATION
--------------------------------------------------------------------------------

Strategy interface:
- `on_book_update(BookSnapshot, StrategyState) -> optional OrderIntent`

Current baseline behavior:
- computes microprice-style fair value from top-of-book
- applies inventory skew and spread model
- enforces minimum edge before emitting intent
- applies inventory-based size shrink
- supports symbol-specific parameter overrides

Trigger gating:
- minimum interval gating
- minimum mid move gating
- minimum imbalance move gating

Readiness gating:
- can require all symbols synchronized before global trading
- can allow per-symbol readiness for partial trading

Outcome:
- intent is converted to command(s) by order management policy

--------------------------------------------------------------------------------
5) ORDER MANAGEMENT, RISK, AND EXECUTION
--------------------------------------------------------------------------------

Order management:
- baseline one active slot per `(symbol, side)`
- emits `New`, `Replace`, `Cancel`
- replace only when price delta crosses configured threshold

Cancel policies:
- opposite-side-first cancel to reduce stale posture
- stale timeout cancel
- adverse-move cancel
- optional adaptive tuning against target cancel-rate telemetry

Pre-trade risk:
- kill switch check
- max order quantity
- max notional
- max projected absolute position

Gateway:
- signed Binance REST for new/replace/cancel
- retry and backoff controls
- tracks REST weight and throttle error codes
- send-governor applies local pacing and cooldown logic

--------------------------------------------------------------------------------
6) OMS, USER STREAM, AND RECONCILIATION
--------------------------------------------------------------------------------

OMS lifecycle:
- states include pending, live, pending-cancel/replace, rejected, completed
- transitions come from gateway acks and user-stream events

User stream:
- parses `ORDER_TRADE_UPDATE` payloads
- maps exchange event/status into normalized exec reports
- extracts local `hft_<id>` client order identifiers

Reconciliation (optional but important):
- control thread fetches remote open orders
- main compares remote count/snapshot to local OMS/OrderManager estimate
- mismatch counters are tracked
- bounded healing can:
  - clear local live slots absent remotely
  - terminalize stale pending/live states after timeout logic

--------------------------------------------------------------------------------
7) PERSISTENCE AND TELEMETRY
--------------------------------------------------------------------------------

Persistence today:
- append-only execution audit log via lock-free queue + writer thread
- append-only market-data health log via separate queue + writer thread

Runtime telemetry:
- printed periodic stats include:
  - market-data throughput and parse/drop counters
  - queue/latency metrics (including queue-to-strategy percentiles)
  - strategy gating and signal counters
  - execution sends/failures/rejects/fills
  - OMS and reconcile counters
  - PnL and drawdown guard counters
  - websocket liveness and reconnect counters

Gaps:
- no durable queryable order/fill store yet
- no external metrics sink/alerts by default

--------------------------------------------------------------------------------
8) FAILURE MODEL AND SAFETY BEHAVIOR
--------------------------------------------------------------------------------

Expected failure classes and behavior:

- Market-data continuity break
  - symbol trading is gated
  - snapshot reseed requested
  - trading resumes only after reseed/in-sync criteria

- User-stream delay/loss
  - reconcile loop detects drift over time
  - bounded healing corrects stale local lifecycle states

- REST throttling / transport errors
  - retry/backoff and local cooldown engage
  - send governor limits further pressure

- Risk breach or operator intervention
  - pre-trade risk rejects command
  - kill switch blocks further order sends

- Control-path overload risk
  - batch caps and per-tick heal limits bound work

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

In good shape:
- websocket MD ingestion, parse, normalization, lock-free handoff
- L2 sequencing and snapshot-based continuity recovery
- strategy trigger and intent pipeline with per-symbol knobs
